■ 完成させた項目

  ・必須項目 A1: 括弧を含まず、加算と乗算のみから成る数式について
                 中置記法から逆ポーランド記法に変換できる。
  ・必須項目 A2: べき乗を表す二項演算子 ^ を含む数式も変換できる。
                 右結合として実装している。
  ・加点項目 B : 括弧を含む数式も変換できる。
  ・加点項目 C : 減算・除算・剰余算を含む数式も変換できる。
  ・加点項目 D : 変換した逆ポーランド記法の数式を計算し、%f の形式で出力できる。
  ・加点項目 E : スタックに関するプログラムを stack.c と stack.h に、
                 キューに関するプログラムを queue.c と queue.h に記述し、
                 分割コンパイルしている。

■ プログラムの説明

【ファイル構成の方針】

　まず、中置記法から逆ポーランド記法への変換プログラムをどのように実装するか
について考える。プログラム全体の処理は、以下の5つに分類できる。

  (1) ユーザが使用するメインファイル               → main.c
  (2) 中置記法から逆ポーランド記法への変換          → infix_to_rpn.c / .h
  (3) スタック操作                                → stack.c / .h
  (4) キュー操作                                  → queue.c / .h
  (5) エラー処理                                  → error.c / .h

したがって、それぞれの役割に対応したファイルに分割して実装する。


【main.c】

　main.cは入力とモジュールの呼び出しの機能に限定する。MAX_TOKEN_NUMは入力内容
により変更する可能性があるので、使用者が変更できるようにmainに書く。enter関数
による入力、"q"の入力による終了のためのループ、infix_to_rpn関数とcalc_rpn関数
の呼び出しを書く。


【infix_to_rpn.c】

　infix_to_rpn.cではmain.cから入力を受け取り中置記法から逆ポーランド記法に変換
する。分割されたトークンの各要素に対し、以下の操作を行うことにより逆ポーランド
記法へと変換できる（操車場アルゴリズム）。

  1. 数値  → そのままキューへ
  2. (     → そのままスタックへpush
  3. )     → スタックから ( が出るまでpopしてキューへ、( は捨てる
  4. 演算子 → スタックの先頭が ( でなく、かつ先頭の優先度が高い
             （左結合なら同じも含む）間はpopしてキューへ、その後pushする
  5. 最後  → スタックに残った演算子を全部キューへ

　ただし、右結合の演算子（^）は同じ優先度ではpopしない。これにより右側の演算子
が先にスタックに積まれ、掃き出し時に右から順にキューへ出るため、右側から計算
される順番になる。

　キューとスタックを初期化したのち、上の操作を実装する。文字列の判定にはstrcmp
関数を用いる。各演算子の優先度を返すpriority関数はinfix_to_rpn.c内に定義し、
+-を1、*/%を2、^を3として実装する。右結合と左結合を実装するため、isRightAssoc
変数を用いて操作の区別を明示的に行っている。数値・演算子・括弧のいずれにも
当たらないものはエラーとする。

　また、変換前にvalidateInfix関数で入力の検証を行い、不正な中置式（先頭が演算子・
演算子が連続・末尾が演算子）を変換前に弾くようにした。priority関数と
validateInfix関数はinfix_to_rpn.c外で使用しないので、ヘッダファイルには
infix_to_rpn関数のみ記述する。


【stack.c】

　通常機能（initStack, push, pop, isStackEmpty, isStackFull）の他に、スタックの
頂上を参照するpeek関数とデバッグ用のprintStack関数を実装する。STACK_SIZEと
STACK_TYPEのtypedef宣言はヘッダファイルに記述した。

　gSNumを「次にpushする場所のインデックス」として定義する。pushはgStack[gSNum]
に格納後gSNumをインクリメントするため++は後置にする。popはgSNum-1の値を返し
gSNumを減らすため--は前置にする。それぞれオーバーフロー/アンダーフローが
起こらないよう、isStackFull/isStackEmptyによるエラー処理を書く。

　peek関数はpopのインデックスを動かさない版の関数といえる。同様にアンダー
フロー防止のエラー処理を書く。


【queue.c】

　リングバッファ形式で実装する。QUEUE_SIZEとQUEUE_TYPEのtypedef宣言はヘッダ
ファイルに記述した。

　queue_frontとqueue_rearの2つのインデックスを宣言し、rearは次に挿入する位置を
指している。isQueueFullでは(queue_rear+1) % QUEUE_SIZEがqueue_frontと一致するか
で判別する。次のインデックスを返すnextIdx関数を定義し、インデックスの循環管理を
一箇所にまとめた。

　enqueueはpushのインデックス管理をnextIdxに置き換えたものと実装は同じであり、
dequeueは値を取ったあとインデックスを動かし値を返す。それぞれオーバー
フロー/アンダーフロー時のエラー処理を実装する。


【error.c】

　受け取ったメッセージを標準エラー出力で出力しexitする。引数にconstを付けるこ
とで、文字リテラルを受け取っても値を変更しないことを明示的に示している。


【calc_rpn.c】

　変換後に空になっているスタックを計算用スタックとして流用する。逆ポーランド記法
の計算アルゴリズムは以下の通りである。

  1. 数字  → pushする
  2. 演算子 → 2つの数字をpopし、その演算子で計算する。結果をpushする。

　LIFOであるスタックを用いているので、先にpopしたものを変数b（右オペランド）、
次をa（左オペランド）と命名している。計算部はcalculate関数として分離した。
数字と演算子以外が出たときは式が不正なのでエラーを出す。また、除算・剰余算
では0で割ることがないよう、calculate関数内でゼロ除算チェックを行う。

■ 動作確認
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

　実行結果はresult.txtに示す。各項目の実行結果は識別子（--A1--等）で区切っている。

  A1: 加算・乗算のみの式について、優先度（乗算>加算）が正しく反映された
      逆ポーランド記法に変換・計算できていることを確認した。

  A2: べき乗演算子^を含む式について、右結合（4*2^2^3/8 = 4*(2^(2^3))/8 = 128）
      が正しく処理されていることを確認した。

  B:  括弧を含む式について、括弧内の演算が優先されていることを確認した。

  C:  減算・除算を含む式について、左結合が正しく処理されていることを確認した。

  D:  各変換結果に対して計算が正しく行われ、%fで出力されていることを確認した。

■ 工夫点
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

(1) STACK_TYPEとQUEUE_TYPEをchar*に統一
　当初はSTACK_TYPEをcharにしていたが、演算子（char）をpopしてキュー（char*）に
渡す際に型の不一致が生じ、都度キャストが必要になった。両者をchar*に揃えること
でこの問題を解消し、コードの見通しが良くなった。

(2) リングバッファ形式でキューを実装
　通常の配列実装ではdequeueのたびに要素を前詰めするO(n)の操作が必要になるが、
リングバッファではqueue_frontとqueue_rearのインデックスを動かすだけでO(1)で
実現できる。

(3) nextIdx関数でインデックス計算を一箇所にまとめた
　リングバッファのインデックス計算（% QUEUE_SIZE）をnextIdx関数として定義した。
これにより、循環管理のロジックが変わった場合でもnextIdx関数のみ修正すれば良く、
保守性が高まる。

(4) 右結合の処理をif/elseで明示的に分岐
　三項演算子でも書けるが、左結合と右結合でwhile条件の>=と>が異なることを明確に
するため、if(isRightAssoc){...}else{...}の形にした。可読性のための判断である。

(5) validateInfix関数で変換前に入力を検証
　不正な中置式（先頭が演算子・演算子が連続・末尾が演算子）を変換前に弾くよう
にした。infix_to_rpn関数の冒頭で呼び出すことで、変換ロジックと検証ロジックを
分離している。

■ 考察
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

　今回の実装を通じて、スタックとキューを組み合わせることで中置記法から逆ポーランド
記法への変換が体系的に実現できることが分かった。特に、演算子の優先度と結合性と
いう2つの性質をスタックの操作に落とし込む操車場アルゴリズムの設計は、データ構造
の適切な選択がアルゴリズムの実装をいかに単純化するかを示す良い例だと感じた。

　また、スタックとキューをchar*型で統一したことで、数値も演算子も文字列として
一貫して扱うことができた。実数への変換はatof/ftoa関数を介して必要なときだけ行う
設計にしたことで、データの流れが明確になった。

　今回はvalidateInfixによる入力検証を実装したが、検出できない不正な式（例：数値
だけが並ぶ式）は計算後のスタックに複数要素が残ることで間接的に検出できる。入口
での検証と出口での検証を組み合わせることで、より堅牢なエラー処理が実現できると
考える。
