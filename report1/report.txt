■ プログラムの説明

【ファイル構成の方針】

　まず、中置記法から逆ポーランド記法への変換プログラムをどのように実装するか
について考える。プログラム全体の処理は、以下の6つに分割できる。

  (1) ユーザが使用するメインファイル               → main.c
  (2) 中置記法から逆ポーランド記法への変換          → infix_to_rpn.c / .h
  (3) 逆ポーランド記法の数値計算                   → calc_rpn.c / .h
  (4) スタック操作                                → stack.c / .h
  (5) キュー操作                                  → queue.c / .h
  (6) エラー処理                                  → error.c / .h

　このように分割したのは、各ファイルが担う役割をひとつに絞ることで、それぞれが互いの実装の詳細を知らなくてよくなるからである。スタックとキューはそれぞれ独立したデータ構造なので、pushやenqueueといった操作は変換の処理とは切り離して書ける。infix_to_rpn.cはヘッダファイルを通じてこれらを呼び出すだけでよく、中身の実装を意識する必要がない。エラー処理を別ファイルにまとめることで、各ファイルが共通のエラー出力をそのまま使えるようになり、メッセージの管理もしやすくなる。またmain.cを分けておくことで、変換ロジックを別のプログラムから使いたいときにmain.cだけ差し替えれば対応できる。
　(3)逆ポーランド記法の数値計算に関しては、その他のプログラムを完成させてから組み込みたいことから、本プログラムを変換処理と独立したモジュールとして切り離しておき、後から容易に追加できるようにしている。
　このような分割にすることで、各ファイルの独立性が上がり、修正や再利用がしやすい構成になると判断した。
 

【main.c】

　main.cはプログラムをカプセル化するため、入力とモジュールの呼び出しの機能に限定する。MAX_TOKEN_NUMは入力内容により変更する可能性があるので、使用者が変更できるようにmainに書く。加えて、enter関数による入力、"q"の入力による終了のためのループ、infix_to_rpn関数とcalc_rpn関数の呼び出しを書く。


【infix_to_rpn.c】

　infix_to_rpn.cではmain.cから入力を受け取り中置記法から逆ポーランド記法に変換する。レポート要綱のpdfファイルの図1,表2を参考し、変換アルゴリズムを考えた。分割されたトークンの各要素に対し、以下の操作を行うことにより、逆ポーランド記法へと変換できる。

t = 数字          → キューに enqueue
t = "("           → スタックに push
t = 演算子        → ※下記
t = ")"           → ※下記
全トークン処理後 → スタックに残った演算子をすべて enqueue

※ t = 演算子のとき
    t が左結合: 頂上 s の優先度 >= t の優先度 → s を pop してキューへ（繰り返す）→ t を push
    t が右結合: 頂上 s の優先度 >  t の優先度 → s を pop してキューへ（繰り返す）→ t を push
    ※ スタックが空 or 頂上が "(" になったら pop をやめて t を push

※ t = ")" のとき
    "(" が出るまでスタックを pop して enqueue（"(" 自体は捨てる）
    "(" が出る前にスタックが空 → エラー
 
　キューとスタックを用いるため、その2つをイニシャライズしたのち、上の操作を書く。ここで、文字列の判定にはstrcmp関数を用いる。

　また、スタックの頂上がXになったらという条件を実装するため、スタックの頂上を参照する【peek関数】を仮に用いる(後にスタックで実装する)。そして、各演算子の優先度を返す【priority関数】を仮に用いる。【priority関数】は優先度をそれぞれ、+-を1、*/%を2、^を3として実装し、予期されない演算子が入力された場合はエラー出力するようにする。
　演算子の実装に際して、右結合と左結合を実装するため、isRightAssoc変数を実装し、右結合と左結合の操作の区別を明示的に行っている。数値・演算子・括弧のいずれにも当たらないものはエラーにする。
　また、変換前にvalidateInfix関数で入力の検証を行い、不正な中置式（式の先頭が演算子,演算子が連続,"("の直後に演算子,トークンが0個,式の末尾が演算子）を変換前に弾くようにした。priority関数とvalidateInfix関数はinfix_to_rpn.c外で使用しないので、ヘッダファイルにはinfix_to_rpn関数のみ記述する。


【stack.c】

　次に、infix_to_rpn.cで用いたスタック(stack.c)を実装する。通常機能(initStack,pop,push,isStackFull/Empty)の他にスタックの頂上を参照する【peek関数】,デバッグ用のprintStack関数を実装する。また、入力内容によって変更する可能性のあるSTACK_SIZEはヘッダファイルに記述した。
　スタックは授業でやったものと同じ要領で行う。本プログラムではSTACK_TYPEはchar*から変更されることは少ないが、可読性のためにtypedef宣言を行う。これは、ヘッダファイルのプロトタイプ宣言で用いることが予期できるから、ヘッダファイルに記述する。また、g_stack_numを「次pushする場所のインデックス」として定義する。pushはg_stack配列のインデックスがg_stack_numの場所に格納し、その後g_stack_numをインクリメントすることで実装できる。よって++は後置にする。反対にpopは頂点のインデックス=g_stack_num-1の値を返しg_stack_numを減らす必要があるので、--を前置にして書けばよい。また、それぞれにオーバーフロー/アンダーフローが起こらないよう、【isStackEmpty】【isStackFull】を仮に用いて、エラー処理を書く。
　initStack,【isStackEmpty】,【isStackFull】は記述内容自体は簡単であるが、可読性とカプセル化のために関数を作成する。また、この３つは他関数で用いる可能性が高いので、関数の中でも上に配置する。
　【peek関数】は頂上を参照するのみなので、popのインデックスを動かさない版の関数といえる。こちらもアンダーフロー防止のエラー処理を書いて実装する。printStack関数はスタックの内容が出力できれば良いので、各要素を" "で区切り順に出力する。
　スタックの関数はすべて外部ファイルでも実行できるようにしたいので、すべてヘッダファイルに記述する。


教科書との実装の相違点は以下のとおりである。

1.ハンガリアン記法とキャメルケースの混合記法で記述された変数をスネークケースに統一"g_stack_num","g_stack[]"
  可読性(変数の意味の明確化)と変数の記法の統一化を図った。

2.printStack関数から指定したタブ数を開ける機能の削除
  本プログラムではタブ数の指定は必要ないため。

3.peek関数の返り値の型をint->STACK_TYPEへ
　本プログラムではスタックに格納するのは主に文字列型であり、また、typedef宣言することで保守性を向上させている。

4.pop関数の書き方を変更
------------------------------------------------
before:
int x = gStack[gSNum - 1];
gSNum --; 
return x

after:
return gStack[--gSNum];
------------------------------------------------
冗長で必要のない変数xを削除し簡潔に記述した。

5.error処理を別ファイルに変更したことに付随する変更
  前述のとおり、共通のエラー出力を使用できることとメッセージの管理の簡易化を図っている。



【queue.c】

　キュー(queue.c)は高速化を図りリングバッファ形式で実装する。こちらもスタックと同様の理由でQUEUE_SIZEとtypedef宣言はヘッダファイルに記述する。
　queueに必要な関数は,エンキュー、デキュー、初期化、キューがフル/空を返す関数、キューの中身を返す関数、リングバッファ形式より、次のインデックスを返す関数(nextIdx関数)である。
　リングバッファ形式なのでまずg_queue_frontとg_queue_rearの2つを宣言する。rearは今回はstackと同様、次に挿入する位置を指している。C言語においてグローバル変数は0で初期化されるが、可読性のために=0と明示的に書く。
　他の関数で使う可能性の高いinitQueue,isQueueEmpty,isQueueFull,nextIdxは先に記述する。また、リングバッファ形式はフル/空を判別するために要素を一つ開けるので、isQueueFullではg_queue_rear+1をキューのサイズで割った余りがg_queue_frontと一致するかで判別する。
　enqueue関数はpush関数のインデックスをnextIdxで管理したものと実装は同じであり、デキューは値を取ったあと、インデックスを動かし、値を返すのみである。それらを実装し、それぞれオーバーフロー/アンダーフロー時のエラー処理を実装する。
　最後にprintQueue関数を実装するが、これもprintStack関数のインデックスをnextIdxで管理したものに変えるだけである。


教科書との実装の相違点は以下のとおりである。

1.ハンガリアン記法とキャメルケースの混合記法で記述された変数をスネークケースに統一。一部不明瞭な名前の関数のリネーム。"g_queue_front","nextIdx"など
  可読性(変数の意味の明確化)と変数の記法の統一化を図った。
  また、Queuenext関数をnextIdx関数にリネームし、関数名から機能を明確に想起できるようにした。(この変数はqueueの内部でしか使用しないのでqueueの要素は排した)

2.一時変数xをtempにリネーム
  変数名から一時変数とわかるようにリネームしている。

3.printQueue関数から指定したタブ数を開ける機能の削除
  本プログラムではタブ数の指定は必要ないため。

4.error処理を別ファイルに変更したことに付随する変更
  前述のとおり、共通のエラー出力を使用できることとメッセージの管理の簡易化を図っている。


【error.c】

　error.cは受け取った値を単に標準エラー出力で出力し、exitする。constはC演習2ではやっていないが、C演習1にて文字リテラルを扱う際はconstとして値を変更しない、できないことを明示的に書くべきと学んだのでその通り実装する。その後ヘッダファイルを記述する。


【calc_rpn.c】

　逆ポーランド記法の計算の実装を追加する(calc_rpn.c)。
　空になっているはずのスタックを用いる。逆ポーランド記法の計算のアルゴリズムは以下の通りである。
　
　ポーランド記法が格納されているキューが空になるまで、１要素ずつデキューし、各要素ごとに以下の操作をする。
    1.数字 -> pushする
    2.演算子-> 2つ数字をpopしてその演算子を用いて計算する。計算結果をpushする。

　上を実装し、計算部は【calculate関数】として仮に置く。
　今回はLIFOであるスタックを用いているので、可読性のために変数bとして先にpopしてから、2つ目の変数をaと命名している。このようにすることで、calculate関数を"a/b"といった直感的な順で記述できる。なお、数字と演算子以外が出たときは式が不正なのでエラーを返す。
　【calculate関数】では、strcmpを用いて文字を判定し、対応する計算式の結果を返す。割り算関連は0で割ることがないよう、checkDivisor関数という、先にpopした変数が0でないかを確かめる関数を作る。calc_rpn <- calculate <- checkDivisorのように参照しているので、checkDivisorを上に、calculateをその次に、calc_rpnを最後に置く。
　また、計算後にスタックが空でない場合はオペランドが多すぎる（演算子不足）として "too many operands" エラーを出すようにする。これにより validateInfix では検出できない「数値が連続する式（ex: 1 2 3）」「数値と括弧が隣接する式（ex: 1 ( 2 + 3 )）」も間接的に弾けるようになる。

【その他】

　ここまでで完成したプログラムは課題の要求をすべて満たすものではあるが、不正な式が入力された場合、アプリ自体が落ちてしまう(exit関数により)仕様となっている。これは本課題の副題にあたる「電卓プログラム」として不適切である。したがって、エラーのときに、深い階層・他ファイルからmainループに戻れるようなプログラムに改善したい。

　この際、私が考えた解決策は以下の３つである。
・例外処理を用いる
・戻り値をエラーコード専用にし、結果は引数のポインタに書き込む
・入力検証を完全化し、実行時にエラーが発生しない状態を保証する

　戻り値方式は、エラーチェックを呼び出しのたびに書く必要があり、全ての関数を作り直すことになる。また、入力検証を完全化する場合も検証ロジックが膨大になってしまう。
　今回は他プログラムが完成していることもあり、書き換える場所が少なくなることから、例外処理を採用する。

　なお、いずれの方法もC演習2では未修だが、C演習1にて学んだため、実装する。
　実装の為に、<setjmp>ライブラリを用いる。これは、プログラムのある地点を「戻り先」として登録しておき、別の場所からその地点に一気にジャンプして戻ることができる機能を提供する標準ライブラリである。通常のreturnは1つ上の関数にしか戻れないが、setjmp/longjmpを使えば何階層深い場所からでも、登録しておいた地点まで一度に戻れる。

■ 動作確認

　実行結果はresult.txtに示す。各項目の実行結果は識別子（--A1--等）で区切っている。

  A1: 加算・乗算のみの式「3 * 4 + 6 * 2」について確認した。
　　乗算は加算より優先度が高いため、3*4と6*2がそれぞれ先に計算され、その後加算されるべきである。変換結果「3 4 * 6 2 * +」は乗算演算子が加算より前に並んでおり、優先度が正しく反映されている。

  A2: べき乗演算子^を含む式「4 * 2 ^ 2 ^ 3 / 8」について確認した。
　　^は右結合であるため、2^2^3は2^(2^3) = 2^8 = 256と評価されるべきである。変換結果「4 2 2 3 ^ ^ * 8 /」は^が右側から先に処理される順に並んでおり、右結合が正しく反映されている。

  B:  括弧を含む式「3 ^ ( 4 + 3 )」について確認した。
　　括弧内の加算が先に評価されるべきであり、変換結果「3 4 3 + ^」は加算がべき乗より前に並んでいる。よって括弧による優先制御が正しく動作していると判断した。

  C:  減算・除算を含む式「6 - 2 / 3 + 1」について確認した。
　　除算は加減算より優先度が高いため2/3が先に評価され、その後左から順に6 - (2/3) + 1と計算されるべきである。変換結果「6 2 3 / - 1 +」はこの順序を正しく表しており、優先度と左結合が正しく処理されていると判断した。

  D:  式「4 * 5 ^ 2」について確認した。
　　^は*より優先度が高いため5^2が先に評価され4 * 25 = 100となるべきである。変換結果「4 5 2 ^ *」はべき乗が乗算より前に並んでおり、計算結果も100.000000と一致するため、%fによる出力も含め正しく動作していると判断した。

■ 工夫点

(1) リングバッファ形式でキューを実装
　通常の配列実装ではdequeueのたびに要素を前詰めするO(n)の操作が必要になるが、リングバッファではg_queue_frontとg_queue_rearのインデックスを動かすだけでO(1)で実現できる。

(2) 入口と出口の二段構えで不正な式を排除
　不正な中置式の検出を、入口（validateInfix）と出口（calc_rpn末尾）の2箇所で行う設計とした。
　入口のvalidateInfix関数では、隣接するトークンの種類を確認することで、「先頭が演算子」「演算子の連続」「"("の直後に演算子」「末尾が演算子」「トークン0個」といった明らかな書き方の誤りを変換前に弾く。
　しかし、validateInfixだけでは「1 2 3」のような数値が連続する式や、「1 ( 2 + 3 )」のような数値と括弧が隣接する式（暗黙の乗算は実装していないので不正）を検出できない。これらは隣接トークンの種類を見るだけでは判別が難しい一方、計算後にスタックが空にならないという形で顕在化する。
　そこで、calc_rpnの末尾で「スタックに余分な要素が残っていれば"too many operands" エラー」とすることで、validateInfixで捕まらないケースを間接的に弾けるようにした。
　これは入口での構文チェックと、出口での不変条件チェックを組み合わせる設計であり、入口側を肥大化させずに堅牢性を高めることができた。

(3) 可読性のための諸工夫
　細部の可読性のため、以下の判断を行った。

　・右結合の処理は三項演算子ではなくif(isRightAssoc){...}else{...}で書いた。
	左結合と右結合のwhile条件の差（>=と>）を読み手に明示するためである。
　・結合性の判定は int isRightAssoc = (strcmp(cur, "^") == 0); で1箇所に集約し、while条件自体には判定式を残さなかった。
	条件本体と結合性判定を分離することで、それぞれの意図が読み取りやすくなる。
　・エラーメッセージは "error: 関数名(): 内容" の形式で統一した。
	エラー発生時にどのファイル・関数で起きたかを即座に特定できる。
　・pop関数は return g_stack[--g_stack_num]; の1行で記述した。
	教科書の3行実装に対して不要な一時変数を排し、意図を簡潔に表現している。

■ 考察
