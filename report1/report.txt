■ プログラムの説明

　本節では、プログラムを構築していく過程に沿って順に説明する。後の節で仕様変更や機能追加を行う箇所もあるため、各ファイルの記述内容は時点ごとの状態を反映しており、最終的なソースコードと完全には一致しない場合がある（例：error.cはこの節では exit する仕様として説明するが、後述の【その他】で longjmp による mainループ復帰に置き換える）。
　また、タイトル以外の【】で囲われた関数・変数は現時点では存在しないが仮に用い、後に実装する。



【ファイル構成の方針】

　まず、中置記法から逆ポーランド記法への変換プログラムをどのように実装するかについて考える。プログラム全体の処理は、以下の6つに分割できる。

  (1) ユーザが使用するメインファイル       → main.c
  (2) 中置記法から逆ポーランド記法への変換  → infix_to_rpn.c / .h
  (3) 逆ポーランド記法の数値計算           → calc_rpn.c / .h
  (4) スタック操作                        → stack.c / .h
  (5) キュー操作                          → queue.c / .h
  (6) エラー処理                          → error.c / .h

　このように分割するのは、各ファイルが担う役割をひとつに絞ることで、それぞれが互いの実装の詳細を知らなくてよくなるからである。スタックとキューはそれぞれ独立したデータ構造なので、pushやenqueueといった操作は変換の処理とは切り離して書ける。infix_to_rpn.cはヘッダファイルを通じてこれらを呼び出すだけでよく、中身の実装を意識する必要がない。エラー処理を別ファイルにまとめることで、各ファイルが共通のエラー出力をそのまま使えるようになり、メッセージの管理もしやすくなる。またmain.cを分けておくことで、変換ロジックを別のプログラムから使いたいときにmain.cだけ差し替えれば対応できる。
　(3)逆ポーランド記法の数値計算に関しては、その他のプログラムを完成させてから組み込みたいことから、本プログラムを変換処理と独立したモジュールとして切り離しておき、後から容易に追加できるようにする。

 

【main.c】

　main.cはプログラムをカプセル化するため、入力とモジュールの呼び出しの機能に限定する。MAX_TOKEN_NUMは入力内容により変更する可能性があるので、使用者が変更できるようにmainに書く。加えて、enter関数による入力、"q"の入力による終了のためのループ(enter関数はq入力時-1を返すのでその条件でループを抜ける)、infix_to_rpn関数とcalc_rpn関数の呼び出しを書く。
　※"jmp_buf g_error_jmp;"宣言とwhile文のif節は【その他】にて追加した。



【infix_to_rpn.c】

　infix_to_rpn.cではmain.cから入力を受け取り中置記法から逆ポーランド記法に変換する。レポート要綱のpdfファイルの図1,表2を参考とし、変換アルゴリズムを考える。分割されたトークンの各要素に対し、以下の操作を行うことにより、逆ポーランド記法へと変換できる。

t = 数字          → キューに enqueue
t = "("           → スタックに push
t = 演算子        → ※下記
t = ")"           → ※下記
全トークン処理後 → スタックに残った演算子をすべて enqueue

※ t = 演算子のとき
    t が左結合: 頂上 s の優先度 >= t の優先度 → s を pop してキューへ（繰り返す）→ t を push
    t が右結合: 頂上 s の優先度 >  t の優先度 → s を pop してキューへ（繰り返す）→ t を push
    ※ スタックが空 or 頂上が "(" になったら pop をやめて t を push

※ t = ")" のとき
    "(" が出るまでスタックを pop して enqueue（"(" 自体は捨てる）
    "(" が出る前にスタックが空 → エラー
 
　まず、infix_to_rpn関数を作り、キューとスタックを用いるため、その2つをイニシャライズしたのち、上の操作を書く。ここで、文字列の判定にはstrcmp関数を用い、可読性の向上のため、現在操作しているトークンの要素を"cur"と置き用いる。
　また、スタックの頂上がXになったらという条件を実装するため、スタックの頂上を参照する【peek関数】を仮に用いる。そして優先度を比較するため、各演算子の優先度を返す【priority関数】を仮に用いる。【priority関数】は優先度をそれぞれ、+-を1、*/%を2、^を3として実装し、予期されない演算子が入力された場合はエラー出力するようにする。
　演算子の実装に際して、右結合と左結合を実装するため、is_right_assoc変数を実装し、右結合と左結合の操作の区別を明示的に行う。数値・演算子・括弧のいずれにも当たらないものはエラーにする。このとき、エラーメッセージを返しexitする【error_exit関数】を仮に用いる。※
　また、変換前にvalidate_infix関数で入力の検証を行い、不正な中置式（式の先頭が演算子,演算子が連続,"("の直後に演算子,トークンが0個,式の末尾が演算子）を変換前に弾くようにする。こちらも同じ要領でstrcmp関数で文字列を判定し実装する。priority関数とvalidate_infix関数はinfix_to_rpn.c外で使用しないので、ヘッダファイルにはinfix_to_rpn関数のみ記述する。

※その他にて【error_exit関数】は名称を変更する。



【stack.c】

　次に、infix_to_rpn.cで用いたスタック(stack.c)を実装する。通常機能(init_stack,pop,push,is_stack_full / is_stack_empty)の他にスタックの頂上を参照する【peek関数】,デバッグ用のprint_stack関数を実装する。また、入力内容によって変更する可能性のあるSTACK_SIZEはヘッダファイルに記述する。
　スタックは授業でやったものと同じ要領で行う。本プログラムではSTACK_TYPEをchar*以外に変更することは少ないが、可読性のためにtypedef宣言を行う。これはヘッダファイルのプロトタイプ宣言で用いることが予期できるから、ヘッダファイルに記述する。また、g_stack_numを「次pushする場所のインデックス」として定義する。pushはg_stack配列のインデックスがg_stack_numの場所に格納し、その後g_stack_numをインクリメントすることで実装できる。よって++は後置にする。反対にpopは頂点のインデックス=g_stack_num-1の値を返しg_stack_numを減らす必要があるので、--を前置にして書けばよい。また、それぞれにオーバーフロー/アンダーフローが起こらないよう、is_stack_empty/is_stack_fullを用いて、エラー処理を書く。
　init_stack,【is_stack_empty】,【is_stack_full】は記述内容自体は簡単であるが、可読性とカプセル化のために関数を作成する。また、この３つは他関数で用いる可能性が高いので、ファイルの中でも上に配置する。
　【peek関数】は頂上を参照するのみなので、popのインデックスを動かさない版の関数といえる。こちらもアンダーフロー防止のエラー処理を書いて実装する。print_stack関数はスタックの内容が出力できれば良いので、各要素を" "で区切り順に出力する。
　スタックの関数はすべて外部ファイルでも実行できるようにしたいので、すべてヘッダファイルに記述する。


教科書との実装の相違点は以下のとおりである。

1.グローバル変数の接頭辞を g から g_ に改め、変数全体をキャメルケースから snake_case に統一（"gSNum"→"g_stack_num"、"gStack"→"g_stack"）
  教科書はハンガリアン記法(g)とキャメルケースの混合だったが、グローバルを示す接頭辞は g_ として残しつつ、記法を snake_case に揃えることで可読性と統一性を図る。

2.print_stack関数から指定したタブ数を開ける機能の削除
  本プログラムではタブ数の指定は必要ないため。

3.peek関数の返り値の型をint->STACK_TYPEへ
　本プログラムではスタックに格納するのは主に文字列型であり、また、typedef宣言することで保守性を向上させる。

4.pop関数の書き方を変更
------------------------------------------------
before:
int x = gStack[gSNum - 1];
gSNum --; 
return x

after:
return g_stack[--g_stack_num];
------------------------------------------------
冗長で必要のない変数xを削除し簡潔に記述する。

5.error処理を別ファイルに変更したことに付随する変更
  教科書ではpush/pop/peek内に fprintf と exit を直接記述するが、本実装ではこれらを raise_error("error: push(): Stack is full") のような呼び出しに置き換える。エラー出力の形式を一元管理できるようになる。



【queue.c】

　キュー(queue.c)は高速化を図りリングバッファ形式で実装する。こちらもスタックと同様の理由でQUEUE_SIZEとtypedef宣言はヘッダファイルに記述する。
　queueに必要な関数は,エンキュー、デキュー、初期化、キューがフル/空を返す関数、キューの中身を返す関数、リングバッファ形式より、次のインデックスを返す関数(next_idx関数)である。
　リングバッファ形式なのでまずg_queue_frontとg_queue_rearの2つを宣言する。rearは今回はstackと同様、次に挿入する位置を指している。C言語においてグローバル変数は0で初期化されるが、可読性のために=0と明示的に書く。
　他の関数で使う可能性の高いinit_queue,is_queue_empty,is_queue_full,next_idxは先に記述する。また、リングバッファ形式はフル/空を判別するために要素を一つ開けるので、is_queue_fullではg_queue_rear+1をキューのサイズで割った余りがg_queue_frontと一致するかで判別する。
　enqueue関数はpush関数のインデックスをnext_idxで管理したものと実装は同じであり、デキューは値を取ったあと、インデックスを動かし、値を返すのみである。それらを実装し、それぞれオーバーフロー/アンダーフロー時のエラー処理を実装する。
　最後にprint_queue関数を実装するが、これもprint_stack関数のインデックスをnext_idxで管理したものに変えるだけである。


教科書との実装の相違点は以下のとおりである。

1.グローバル変数の接頭辞を g から g_ に改め、変数全体をキャメルケースから snake_case に統一（"g_queue_front" など）。一部不明瞭な名前の関数もリネームする。
  教科書はハンガリアン記法(g)とキャメルケースの混合だったが、グローバルを示す接頭辞は g_ として残しつつ、記法を snake_case に揃えることで可読性と統一性を図る。
  また、Queuenext関数をnext_idx関数にリネームし、関数名から機能を明確に想起できるようにする。(この関数はqueueの内部でしか使用しないのでqueueの要素は名前から排する)

2.一時変数xをtempにリネーム
  変数名から一時変数とわかるようにリネームする。

4.error処理を別ファイルに変更したことに付随する変更

  これらを raise_error("error: enqueue(): Queue is full") のような呼び出しに
  置き換える。エラー出力の形式を一元管理できるようになる。



【error.c】

　error.cは受け取った値を単に標準エラー出力で出力し、exitし、【error_exit関数】と命名する（この動作は後述の【その他】で改善する）。また、C演習1にて文字リテラルを扱う際はconstとして値を変更しない、できないことを明示的に書くべきと学んだのでその通り実装する。その後ヘッダファイルを記述する。



【calc_rpn.c】

　逆ポーランド記法の計算の実装を追加する(calc_rpn.c)。
　空になっているはずのスタックを用いる。逆ポーランド記法の計算のアルゴリズムは以下の通りである。
　
　ポーランド記法が格納されているキューが空になるまで、１要素ずつデキューし、各要素ごとに以下の操作をする。
    1.数字  -> pushする
    2.演算子-> 2つ数字をpopしてその演算子を用いて計算する。計算結果をpushする。

　上を実装し、計算部は【calculate関数】として仮に置く。
　今回はLIFOであるスタックを用いているので、先にpopしたものを変数b、次にpopしたものを変数aと命名する。このようにすることで、calculate関数を"a/b"といった直感的な順で記述できる。なお、数字と演算子以外が出たときは式が不正なのでエラーを返す。
　【calculate関数】では、strcmpを用いて文字を判定し、対応する計算式の結果を返す。割り算関連は0で割ることがないよう、check_divisor関数という、先にpopした変数が0でないかを確かめる関数を作る。calc_rpn <- calculate <- check_divisorのように参照しているので、check_divisorを上に、calculateをその次に、calc_rpnを最後に置く。
　また、計算後にスタックが空でない場合はオペランドが多すぎる（演算子不足）として "too many operands" エラーを出すようにする。これにより validate_infix では検出できない「数値が連続する式（例: 1 2 3）」「数値と括弧が隣接する式（例: 1 ( 2 + 3 )）」も間接的に弾けるようになる。



【その他】

　ここまでで完成したプログラムは課題の要求をすべて満たすものではあるが、不正な式が入力された場合、アプリ自体が落ちてしまう(exit関数により)仕様となっている。これは本課題の副題にあたる「電卓プログラム」として不適切である。したがって、エラーのときに、深い階層・他ファイルからmainループに戻れるようなプログラムに改善したい。

　この際、私が考えた解決策は以下の３つである。
・例外処理を用いる
・戻り値をエラーコード専用にし、結果は引数のポインタに書き込む
・入力検証を完全化し、実行時にエラーが発生しない状態を保証する

　戻り値方式は、エラーチェックを呼び出しのたびに書く必要があり、ほぼ全ての関数を書き換える必要がある。また、入力検証を完全化する場合も検証ロジックが膨大になってしまう。
　今回は他プログラムが完成していることもあり、書き換える場所が少なくなることから、例外処理を採用する。
　なお、例外処理はC演習2では未修だが、C演習1にて学んだため、実装する。
　実装の為に、<setjmp.h>をインクルードし、標準ライブラリの setjmp/longjmp 関数を用いる。これは、プログラムのある地点を「戻り先」として登録しておき、別の場所からその地点に一気にジャンプして戻ることができる機能を提供する仕組みである。通常のreturnは1つ上の関数にしか戻れないが、setjmp/longjmpを使えば何階層深い場所からでも、登録しておいた地点まで一度に戻れる。具体的には、main.c の setjmp(g_error_jmp) を「戻り先」、error.c の longjmp(g_error_jmp, 1) を「ジャンプ元」として、両者をg_error_jmpという戻り先を保存する変数で結びつける。
　main.cでは、jmp_buf型の変数 g_error_jmp をグローバルに宣言し、while文の中でsetjmp(g_error_jmp)を呼ぶことでループ先頭を戻り先として登録する。setjmpは通常時に0を返すため、戻り値が0のときのみ infix_to_rpn と calc_rpn を実行するようにする。else側にはユーザに次の入力を促すメッセージを書いておく。
　error.cでは、error_exit関数の末尾を exit(1) から longjmp(g_error_jmp, 1) に置き換える。これによりエラー発生時にはmain.cで登録した戻り先まで一気にジャンプし、setjmpは今度は0以外を返すためif文内はスキップされ、次の入力を受け付ける処理に進む。
　関数の機能の変更に合わせて、error_exit関数と呼称してきたものを、より適切なraise_error関数としてリネームする。

■ 動作確認

　実行結果はresult.txtに示す。各項目の実行結果は識別子（--A1--等）で区切っている。

  A1: 加算・乗算のみの式「3 * 4 + 6 * 2」について確認した。
	乗算は加算より優先度が高いため、3*4と6*2がそれぞれ先に計算され、その後加算されるべきである。変換結果「3 4 * 6 2 * +」は乗算演算子が加算より前に並んでおり、優先度が正しく反映されている。

  A2: べき乗演算子^を含む式「4 * 2 ^ 2 ^ 3 / 8」について確認した。
　　^は右結合であるため、2^2^3は2^(2^3) = 2^8 = 256と評価されるべきである。変換結果「4 2 2 3 ^ ^ * 8 /」は^が右側から先に処理される順に並んでおり、右結合が正しく反映されている。さらに、計算結果も4 * 256 / 8 = 128となるべきところ、128.000000と一致している。

  B:  括弧を含む式「3 ^ ( 4 + 3 )」について確認した。
　　括弧内の加算が先に評価されるべきであり、変換結果「3 4 3 + ^」は加算がべき乗より前に並んでいる。よって括弧による優先制御が正しく動作していると判断した。

  C:  減算・除算を含む式「6 - 2 / 3 + 1」について確認した。
　　除算は加減算より優先度が高いため2/3が先に評価され、その後左から順に6 - (2/3) + 1と計算されるべきである。変換結果「6 2 3 / - 1 +」はこの順序を正しく表しており、優先度と左結合が正しく処理されていると判断した。

  D:  式「4 * 5 ^ 2」について確認した。
　　^は*より優先度が高いため5^2が先に評価され4 * 25 = 100となるべきである。変換結果「4 5 2 ^ *」はべき乗が乗算より前に並んでおり、計算結果も100.000000と一致するため、%fによる出力も含め正しく動作していると判断した。

  E:  分割コンパイルについて確認した。
　　演習室のLinux環境にて compile.txt のコマンド（sh compile.txt）を実行し、stack.c / stack.h / queue.c / queue.h を含む全ソースファイルが正しく結合されてコンパイルに成功し、実行ファイルが生成されることを確認した。

  1:  式「5 * 2 % 3」について確認した。
　　*と%は同じ優先度であり、左結合であるため、5*2が先に評価され10 % 3 = 1と計算されるべきである。計算結果は1.000000と一致し、剰余算の計算についても正しく動作していると判断した。

  2:  不正な式を入力した後の動作について確認した。
　　「) + 3 2」（括弧の対応不正）を入力するとエラーメッセージが表示され、プログラムが終了せずに次の入力プロンプトが表示された。続けて「1 2 3」（オペランド過多）を入力した場合も同様にエラーを通知して次の入力を受け付けており、エラー発生後もmainループへ復帰して継続使用できることを確認した。

■ 工夫点

(1) リングバッファ形式でキューを実装
　通常の配列実装ではdequeueのたびに要素を前詰めするO(n)の操作が必要になるが、リングバッファではg_queue_frontとg_queue_rearのインデックスを動かすだけでO(1)で実現できる。

(2) 剰余算への対応
　本実装は加点項目Cの「減算・除算」までで要求を満たすが、逆ポーランド記法変換アルゴリズムが四則演算と同じ枠組みで剰余算 % も扱えることに気づき、追加実装を行った。実際に必要だった変更はpriority関数で % の優先度を2と返す1行と、calculate関数で fmod を呼ぶ数行のみであった。除算で作っていたcheck_divisor関数も0除算チェックとしてそのまま再利用できた。result.txtの1が実行例となる。

(3) 入口と出口の二重チェックで不正な式を排除
　不正な中置式の検出を、入口（validate_infix）と出口（calc_rpn末尾）の2箇所で行う設計とした。
　なお前提として、補助プログラムの enter 関数が字句レベルで、不正な数値形式（小数点が2個など）・未知の文字・トークン数超過といった「そもそもトークンに分割できない入力」を弾いてくれている。本実装の工夫は、その後段で扱う中置式としての正しさの検証である。
　入口のvalidate_infix関数では、隣接するトークンの種類を確認することで、「先頭が演算子」「演算子の連続」「"("の直後に演算子」「末尾が演算子」「トークン0個」といった明らかな書き方の誤りを変換前に弾く。
　しかし、validate_infixだけでは「1 2 3」のような数値が連続する式や、「1 ( 2 + 3 )」のような数値と括弧が隣接する式（暗黙の乗算は実装していないので不正）を検出できない。これらは隣接トークンの種類を見るだけでは判別が難しい一方、計算後にスタックが空にならないという形で顕在化する。
　そこで、calc_rpnの末尾で「スタックに余分な要素が残っていれば"too many operands" エラー」とすることで、validate_infixで捕まらないケースを間接的に弾けるようにした。
　これは入口での構文チェックと、出口での不変条件チェックを組み合わせる設計であり、入口側を肥大化させずに堅牢性を高めることができた。result.txtの2が実行例となる。

(4) エラーで終了しない対話的な電卓としての作り込み
　当初の実装は不正な式の入力時に exit してプログラムが終了する仕様だったが、本課題の副題「電卓プログラム」に忠実であるため、エラーを通知した上で終了せずに次の入力を受け付け続けるよう改善した。これにより、一度の誤入力でやり直す必要がなく、電卓として連続的に使用できる。実現方法の詳細は【その他】に記す。
　　ただし、補助プログラム lib1.c 内で直接 exit している箇所（不正な数値形式・未知の文字・トークン数超過の検出など）については、自作の raise_error を経由しないため longjmp で復帰させることはできない。これらはトークンに分割する段階で入力が破損しているケースであり、復帰させても処理を継続できないため、本プログラムでは復帰対象外とする。

(5) 可読性のための諸工夫
　細部の可読性のため、以下の判断を行った。

　・右結合の処理は三項演算子ではなくif(is_right_assoc){...}else{...}で書いた。
	左結合と右結合のwhile条件の差（>=と>）を読み手に明示するためである。
　・結合性の判定は int is_right_assoc = (strcmp(cur, "^") == 0); で1箇所に集約し、while条件自体には判定式を残さなかった。
	条件本体と結合性判定を分離することで、それぞれの意図が読み取りやすくなる。
　・エラーメッセージは "error: 関数名(): 内容" の形式で統一した。
	エラー発生時にどのファイル・関数で起きたかを即座に特定できる。
　・pop関数は return g_stack[--g_stack_num]; の1行で記述した。
	教科書の3行実装に対して不要な一時変数を排し、意図を簡潔に表現している。
　・命名はC言語の慣習に従い、関数・変数ともに英語のスネークケースで統一した。グローバル変数には接頭辞として g_（g_stack_num など）を付け、ローカル変数と区別できるようにしている。エンコーディング問題などを回避するためコメントも全て英語で記述している。
	日本語ローマ字や記法混在を避けることで、ソースファイル全体の見た目に一貫性を持たせている。

■ 考察

(1) 途中の仕様変更と機能追加から学んだ「モジュール化」の本質について
　本プログラムでは、スタック、キュー、エラー処理（error.c）をそれぞれ独立したモジュールとして構築する方針をとったが、その後の「エラー処理の大域ジャンプへの変更」と「数値計算機能（calc_rpn.c）の後付け」という2つの大きな作業を通じて、モジュール化の価値を実感した。
　各ファイルが他ファイルのエラー処理の具体的な中身や、スタックの内部構造（配列の実装など）に依存したコードになっていたら、一箇所の変更や機能追加のたびに、すでに完成していたバグのないコードまでドミノ倒しのように書き換えるリスクが発生していたはずである。しかし、今回は各モジュールの役割を1つに絞り、内部を隠蔽してインターフェースのみで繋ぐ「カプセル化」を意識して構築していたため、他のファイルに一切影響を与えずに中身の入れ替えや再利用ができた。モジュール化とは単にファイルを物理的に分けることではなく、「他のファイルの実装を意識しなくてよい状態」を作ることこそが本質であり、それがプログラムの安全性や拡張性を劇的に高めるのだと、身を以て深く理解した。

(2)validate_infix と calc_rpn による二段構えのエラーチェックの効率の良さ
　はじめ、不正な中置式をすべて変換前の validate_infix だけで見つけようと考えたが、チェックするためのプログラムが非常に複雑になってしまった。これは一部のケースにおいて、単に隣り合うトークンを見るだけではなく、式全体の構造を正しく解析しないとエラーだと断定しにくいものがあることによるものである。
　これに対し、今回の実装のように「入り口（validate_infix）では演算子の連続などの単純なミスを弾き、出口（calc_rpn）で計算が終わった後のスタックの残数を確認する」という二段構えの設計にしたのは効率が比較的良くできたと思う。逆ポーランド記法への変換プロセスそのものが、式の構造をチェックする役割を果たしてくれているため、最後のスタックの状態（要素が1つだけ残っているはずという条件）を見るだけで、複雑な構文エラーも自動的に、かつ簡単な処理で検出できるようになった。
　　一方で、この設計には「不正な式を弾く」という1つの関心事が入口（validate_infix）と出口（calc_rpn末尾）の2箇所に分散するという弱点もある。検証ルールを修正・追加するときに、どちらで対応すべきかを両方確認する必要があり、保守の際に見通しが悪くなりやすい。今回はコメントで相互に参照を張ることでこの弱点を補ったが、堅牢性（検出漏れの少なさ・入口の単純さ）と保守性（修正箇所のまとまり）は一般にトレードオフの関係にあり、両者のバランスを意識して設計を選ぶことが重要だと感じた。
